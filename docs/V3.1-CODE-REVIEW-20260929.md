# bashGate v3.1 代码审查 + 设计可行性评估（2026-09-29）

> 审查对象：bashgate/ 目录五件套（v3.1，服务器实跑版本）
> 审查视角：前两轮攻击（PWN-REPORT-BASHGATE-20260929.md）的红队复核 + 静态代码审查
> 结论先行：**架构方向正确，但有一个致命 bug（超时杀不掉租户进程）和三处"写了但没生效"的配置**

## 一、你的设计目标逐条评估

| 你的目标 | 能否实现 | 现状 | 缺口/机制 |
|----------|---------|------|-----------|
| 程序跑在 /software/web-shell，只有程序用户权限 | ✅ 已实现 | `User=webshell` + 目录 750 | 攻击者实测：源码、audit、/www 全部不可读 |
| webshell 权限只在 web-shell 子目录内 | ⚠️ 基本成立 | ProtectSystem=full + ProtectHome=yes + DAC | POSIX 用户天然能**读**世界可读文件（/etc/passwd 等），这是 uid 模型的固有属性；要字面意义的"只在目录内"需要 chroot/mount ns 包装，成本高收益低。当前配置已把"能写的"和"能看的机密"收住 |

## 二、致命问题：30s 超时对租户进程无效（🔴 必修）

**bashgate.js:92-95**

```js
const timer = setTimeout(() => {
  killed = true;
  try { process.kill(-child.pid, 'SIGKILL'); } catch (e) { ... }
}, CMD_TIMEOUT_MS);
```

**问题链条**：
1. v3 用 `sudo -n -u usera bash` 降权。sudo 是 SUID-root：`spawn` 出来的 child（sudo 父进程）ruid=996(webshell)、euid=0；它 fork 出来的租户 bash 被切成 ruid=euid=1001。
2. 超时时 webshell(996) 对进程组发 `kill(-pgid, SIGKILL)`：内核逐个成员检查信号权限——**sudo 父进程 ruid=996 → 能杀；租户 bash/sleep/死循环 ruid=1001 → EPERM，跳过**。
3. 结果：sudo 被杀、`close` 事件触发、请求返回 `TIMEOUT_KILLED`——**但租户进程变成孤儿继续跑**。`bash -c 'sleep 31'` 会被 bash 优化成直接 exec sleep，sleep(ruid 1001) 网关照样杀不掉。
4. webshell 对 uid=1001 进程**没有任何信号权限**（POSIX 规则），所以没有任何代码路径能回收它。租户起一个 `while :; do :; done`（连 setsid 都不用），就得到一个**网关自己永远停不掉的死循环**；攒到服务级 `pids.max=1857` 后网关连 sudo 都 fork 不出来，整机沙箱瘫痪，只能 `systemctl restart`（systemd 的 KillMode=control-group 以 root 身份清场）。

**修复（cgroup 必杀，与 uid 无关）**：

```js
const timer = setTimeout(() => {
  killed = true;
  // cgroup.kill 杀全组（含 setsid 逃逸者），且不依赖信号权限
  try { fs.writeFileSync(`${CGROOT}/${conf.sys}/cgroup.kill`, '1'); }
  catch (e) { try { process.kill(-child.pid, 'SIGKILL'); } catch (_) {} }
}, CMD_TIMEOUT_MS);
```

注意两点：
- `cgroup.kill` 文件在 cgroup v2 上**不需要任何 controller**，只要目录属主是 webshell（Delegate 已 chown）——**即使在当前 delegation 失效状态下这行代码也能工作**；
- 当前写法按租户组整体杀，会连坐同一租户的其他并发请求（最多 3 个）。讲究的做法是**每请求子组**：`CGROOT/<user>/req-<n>/` 写入 child.pid，超时杀该子组，close 后清理。粗粒度版（整租户组杀）在 MAX_CONCURRENT=3 的语义下也可接受。

## 三、"写了但没生效"三件套（🔴🔴🔴）

### 3.1 per-租户 cgroup 限额实际未生效

**服务器实锤**（第二轮攻击实测）：`/sys/fs/cgroup/system.slice/bashgate.service/cgroup.subtree_control` 内容为**空** → 子组 `usera/` 下**不存在** memory.max / pids.max 文件（cpu.max 缺席是正常的——cpu 不在 Delegate 列表；**memory.max/pids.max 缺席不正常**）。

**推理链**：unit 写了 `Delegate=memory pids`，但运行中的 systemd 若没吃到新配置（**改完 unit 没有 `systemctl daemon-reload`**，restart 用的还是内存里的旧配置），委派没发生 → subtree_control 空 → 子组没有 controller 接口文件 → `ensureCgroups()` 里 `writeFileSync(memory.max)` 抛 ENOENT → 只进 problems 数组 + console.warn（服务日志，无人看）→ **静默无限额**。

后果：唯一的内存约束是服务级 `MemoryMax=300M`，它**把网关自己也罩进去**——租户拆成多个小进程分配内存，让 node（RSS ~95M）成为 cgroup 内最大进程，OOM killer 就会**杀掉网关本体** → Restart=on-failure 重启 → 外部循环重放即得 crash-loop DoS。

**修复**：
```bash
systemctl daemon-reload && systemctl restart bashgate
systemctl show bashgate -p Delegate,PrivateTmp,MountFlags   # 确认吃到新配置
```
代码侧加自检（启动时读回断言，失败直接拒绝服务而不是 warn）：
```js
if (!fs.existsSync(`${CGROOT}/${u}/memory.max`)) throw new Error(`cgroup delegation broken: ${u}`);
```
另建议给租户子组写 `memory.oom.group=1`：OOM 时整租户组团灭，把网关摘出被杀名单。

### 3.2 CPU 无限额（三代同款）

`Delegate=memory pids` 不含 cpu，unit 也没有 CPUQuota——租户可用满全部核（第一轮就是这么冻住整机的）。两行修：

```
# unit:
Delegate=memory pids cpu          # 然后代码里给每个租户写 cpu.max，如 "50000 100000"（半核）
CPUQuota=150%                     # 兜底：整个服务（网关+全部租户）最多 1.5 核，保住宿主机
```

**sudoers 一行兜底（强烈推荐，与 cgroup 无关的硬保险）**：sudo ≥1.9.5 支持 rlimit Defaults，Ubuntu 24.04 的 1.9.15 支持：

```
Defaults:webshell rlimit_cpu=30, rlimit_nproc=64
```

`rlimit_cpu=30` = 每条命令最多烧 30 秒 CPU（超了 SIGXCPU）——即使 cgroup CPU 限额又失效，死循环也烧不过 30 秒 CPU 时间。`rlimit_nproc=64` 把 v2 的每租户 64 进程上限找回来（现在服务级 1857 太松）。

### 3.3 PrivateTmp 在这台机器三代都没生效

v1/v2/v3 三轮实测，租户内挂载表 `/tmp` 都是宿主 ext4 而非私有 tmpfs（unit 里 `PrivateTmp=yes` 一直写着）。ProtectSystem=full 生效过（/etc 确实 ro），说明 mount namespace 存在，唯独 PrivateTmp 没上——**最可疑也是 daemon-reload 缺失**，但需要在 root shell 上确认：

```bash
systemctl show bashgate -p PrivateTmp -p MountFlags -p Delegate
journalctl -u bashgate -b | grep -iE "privatetmp|mount"
```

即便修好，记住 PrivateTmp 是**服务级**不是**租户级**（v1 的教训）：它只隔离"服务 vs 系统"。租户间 /tmp 的现实方案就是现在这套 **TMPDIR 指向 `~/.tmp`**（setup.sh 已建 700 目录 ✅），但要明白它是"君子协议"——程序硬编码 /tmp 就穿透。想硬隔离只有 per-spawn mount ns（`unshare -m` 需要 CAP_SYS_ADMIN 或 userns，当前架构没有；不建议为它加）或接受现状+文档化"租户临时敏感数据勿放 /tmp"。

## 四、NNP=0 回归：sudo 方案的结构性代价（🟠）

对比两代：v2 网关=root，`spawn('bash',{uid})` 直接 setuid → 子进程继承 **NoNewPrivileges=1**，全机 13 个 SUID（sudo/su/mount/fusermount3/passwd…）在租户内全部变废铁（第一轮实测）。v3 网关=webshell，setuid 干不了了 → 借道 SUID sudo → **service 里 NoNewPrivileges 被去掉**（不去掉 sudo 自己就被废了）→ 租户内 SUID 全线复活（第二轮实测 NNP=0）。

目前实际风险有限（sudo/su 需要密码——攻击者实测系统密码≠API 密码；mount 无 user 挂载项；fusermount3 无 userns 配合难成事），但它把"SUID 提权"这一整类攻击面（包括未来 sudo/mount 的 CVE）重新打开了。

**三个方案，推荐 B**：

- **A. 维持 sudo 方案** + 接受 NNP=0 + 用 sudoers rlimits（见 3.2）和系统补丁兜底。代价：SUID 面永久敞开。
- **B.（推荐）网关保留 webshell + 能力位降权替代 sudo**：
  ```
  # unit:
  AmbientCapabilities=CAP_SETUID CAP_SETGID
  NoNewPrivileges=yes          # 恢复！NNP 不阻止 ambient caps 的继承，只挡 SUID/file-caps
  ```
  ```js
  // 代码回到 v2 的直接 spawn（node 进程持有 CAP_SETUID，setuid 系统调用合法）：
  const child = spawn('/usr/bin/bash', ['-c', cmd], { uid, gid, cwd: conf.home, env, detached: true });
  ```
  sudoers/sudo 整条链路删除；NNP=1 回归 → 租户 SUID 再度全废；网关妥协后能变任一 uid（比 sudo 白名单宽），但代码里 UIDS 白名单本来就硬编码了 usera/userb，可控。
- **C. 回到 v2 的 root 网关**：最强隔离但 TCB=root，你 v3 的动机（降权网关）就白费了。

注意：**无论选哪个，第二节的 cgroup.kill 修复都不可省**——信号权限的 ruid 边界在 A/B 两个方案下都挡着 webshell。

## 五、其他发现（🟡）

1. **hidepid 仍未开**：租户可见全机进程表与 cmdline——第二轮实锤读到**管理员本人 root shell 的核验脚本**（你当时在跑"核对A: setsid逃逸"）。管理员手动调试的内容对租户是裸的。修复：`/etc/fstab` 的 proc 行加 `hidepid=2`（或 systemd .mount 覆盖）。
2. **HOME 错位**：`/etc/passwd` 里 usera 家目录是 `/home/usera`，设计家目录是 `/data/userA`。sudo env_reset 后 HOME 大概率被改写为 /home/usera——而它在 ProtectHome=yes 下是隐藏的空 tmpfs，租户程序写 `~` 会失败。修复：`usermod -d /data/userA usera`（userb 同理）。
3. **cgroup.procs 竞态**（代码注释已认）：spawn 后才写 cgroup.procs，毫秒窗口内 fork 的子进程落在组外。v3.1 下影响变小（反正限额也没生效😅），修复 cgroup 限额后建议每请求子组 + 写入后校验。
4. 小项：`error` 与 `close` 都会 `running-1`，理论上重复递减（有 Math.max(0,) 钳制，无害）；/login 无速率限制（靶场可接受）。

## 七、修复优先级与重新上线自检清单

**改动清单**（按序）：
1. `systemctl daemon-reload && restart`，确认 Delegate/PrivateTmp 吃到新配置
2. bashgate.js：超时改 `cgroup.kill`（建议每请求子组）
3. unit：`Delegate=memory pids cpu` + `CPUQuota=150%`；代码给租户写 `cpu.max`
4. sudoers 追加：`Defaults:webshell rlimit_cpu=30, rlimit_nproc=64`
5. （择 B）unit 换 `AmbientCapabilities=CAP_SETUID CAP_SETGID` + `NoNewPrivileges=yes`，代码回归直接 spawn，删 sudo
6. `usermod -d /data/userA usera`（userb 同理）
7. /proc 挂 hidepid=2
8. 租户组 `memory.oom.group=1`；ensureCgroups 启动自检改硬失败

**上线自检（用攻击者的老命令复查）**：
